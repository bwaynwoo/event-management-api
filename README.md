# Event Management API

REST API для управления мероприятиями.
## Технологии

- .NET 10
- ASP.NET Core Web API
- Swagger/OpenAPI
- PostgreSQL

## Требования

- [.NET 10](https://dotnet.microsoft.com/download)
- PostgreSQL

## Настройка строки подключения
- Откройте файл appsettings.json в проекте EventManagementApi
- Найдите секцию ConnectionStrings (если её нет — добавьте)
- Укажите строку подключения к вашей базе данных PostgreSQL:
```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=localhost;Port=5432;Database=EventManagementDb;Username=postgres;Password=your_password"
  }
}
```
Параметры подключения:
- Host — адрес сервера PostgreSQL (по умолчанию localhost)
- Port — порт (по умолчанию 5432)
- Database — название базы данных
- Username — имя пользователя PostgreSQL
- Password — пароль пользователя

Важно: Не добавляйте appsettings.json с реальными паролями в систему контроля версий. Для локальной разработки используйте appsettings.Development.json или User Secrets

Схема БД управляется миграциями EF Core;.

## Установка и запуск

* Клонировать репозиторий

```bash
git clone https://github.com/bwaynwoo/event-management-api.git
```

* Перейти в репозиторий
```bash
cd event-management-api
```

* Переключиться на ветку sprint-7

```bash
git switch sprint-7
```

* Собрать решение
```bash
dotnet build
```

* Запустить проект
```bash
dotnet run
```

* Открыть Swagger\
После запуска Swagger будет доступен по адресу:
```
http://localhost:5000/swagger/index.html
```

>Порт может отличаться. Точный адрес будет показан в терминале после запуска.

При возникновении ошибок API возвращает JSON-ответ в следующем формате:

```json
{
  "status": <код_статуса>,
  "detail": "<сообщение_об_ошибке>"

```

### HTTP статусы:
| Статус |Описание|
|-------|--|
| 400   |	Ошибка валидации (некорректные данные запроса)
| 404   |	Ресурс не найден (событие с указанным ID отсутствует)
| 409   |   При отсутствии мест возвращается 409 Conflict
| 500   |	Внутренняя ошибка сервера

| Title (string, обязательное); | название события |

### Модель Booking
| Поле|Описание|
|-------------------------------|--|
| Id (Guid, обязательное)       | уникальный идентификатор брони|
| EventId (Guid, обязательное) | идентификатор события, к которому относится бронь| 
| Status (BookingStatus, обязательное) | текущий статус брони|
|CreatedAt (DateTime, обязательное) | дата и время создания брони|
|ProcessedAt (DateTime?, опциональное) | дата и время обработки брони|

#### BookingStatus

| Поле|Описание|
|-----|--|
|Pending | бронь создана, ожидает обработки|
|Confirmed | бронь подтверждена|
|Rejected | бронь отклонена|

### Фоновый сервис
Реализован фоновый сервис, который периодически опрашивает
хранилище на наличие бронирований в статусе Pending.
Для каждой найденной необработанной брони выполняется искусственная
задержка, имитирующая обращение к внешней системе.
После задержки бронь переводится в статус Confirmed.
После смены статуса заполняется поле ProcessedAt.
Обновлённая бронь сохраняется в хранилище.

### Примитивы синхронизации
Используется примитив синхронизации — SemaphoreSlim.

Примитив необходим для предотвращения гонки данных. 
Без его использования может возникнуть следующая ситуация: 
первый поток читает, что есть свободные места, и пытается забронировать. 
В этот момент второй поток может вклиниться, пока первый ещё не успел завершить 
бронирование, и тоже прочитать, что есть свободные места. В итоге можно получить 
ситуацию, когда забронировано место, которого уже нет.

Примитив _lock_ не используется, поскольку он несовместим с асинхронными методами.


### Пример сценария использования
1. Создаём событие
2. По id события создаём бронирование
3. Бронирование создаётся со статусом "Pending"
4. В фоне происходит обработка бронирования и переход статуса в "Confirmed"

### Сценарий овербукинга
1. Создаётся событие с общим количеством мест, равным 5.
2. Одновременно запускается 20 параллельных запросов на бронирование.
3. Потоки конкурируют за доступ к данным о свободных местах.
4. Без синхронизации несколько потоков могут прочитать, что места ещё есть, и попытаться забронировать, превысив лимит.
5. SemaphoreSlim гарантирует, что только 5 запросов завершатся успешно, а 15 получат отказ.
6. Ожидаемый результат: успешных бронирований — ровно 5, остальные 15 завершаются с исключением о нехватке мест.

## 🏗️ Clean Architecture

Проект построен по принципам чистой архитектуры. Разделение на отдельные сборки гарантирует соблюдение направления зависимостей:
внешние слои зависят от внутренних, но не наоборот.

### Назначение слоёв

#### 🟣 Domain (Class Library)
Самый внутренний слой. Содержит бизнес-правила и не зависит ни от чего внешнего.

- **Entities** — доменные сущности (`Event`, `Booking`)
- **Value Objects** — объекты-значения
- **Domain Exceptions** — доменные исключения (`NotFoundException`, `ValidationException`)

#### 🟢 Application (Class Library)
Слой use cases и бизнес-логики приложения. Зависит **только от Domain**.

- **Services** — сервисы приложения (`EventService`, `BookingService`)
- **Interfaces** — интерфейсы портов (`IEventRepository`, `IBookingRepository`)
- **DTOs** — объекты передачи данных (`CreateEvent`, `BookingInfo`)
- **Background Services** — фоновые задачи (`BookingBackgroundService`)

#### 🔴 Infrastructure (Class Library)
Реализует доступ к данным и взаимодействие с внешними системами. Зависит от **Domain и Application**.

- **DataAccess** — `AppDbContext`, миграции EF Core
- **Repositories** — реализации репозиториев (`EventRepository`, `BookingRepository`)
- **Configurations** — конфигурации сущностей (`IEntityTypeConfiguration`)

#### 🔵 Presentation (Web API)
Точка входа в приложение. Зависит от **всех слоёв**.

- **Endpoints** — Minimal API эндпоинты
- **Exception Handling** — обработчики исключений (`GlobalExceptionHandler`)
- **DI Registration** — регистрация зависимостей
