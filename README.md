# Event API

## 🏗️ Архитектура

Система состоит из трёх независимых микросервисов, построенных по принципам чистой архитектуры.

### Состав системы

| Сервис             | База данных           | Порт | Описание                                                      |
|--------------------|-----------------------|------|---------------------------------------------------------------|
| **UserService**    | users (PostgreSQL)    | 5270 | Регистрация, вход, хеширование паролей, генерация JWT-токенов |
| **EventService**   | events (PostgreSQL)   | 5257 | Управление событиями (CRUD), учёт доступных мест              |
| **BookingService** | bookings (PostgreSQL) | 5237 | Создание и отмена броней, лимиты бронирований                 |

Каждый сервис имеет:

- Собственную базу данных
- Собственный контекст БД
- Слои Domain, Application, Infrastructure, Presentation
- Независимые миграции EF Core

### Связи между сервисами

Сервисы не имеют навигационных свойств между сущностями — только идентификаторы:

- `Booking` хранит `UserId` (Guid) и `EventId` (Guid)
- Взаимодействие через HTTP API и сообщения kafka.

## 📡 Поток данных: BookingConfirmed

### Кто публикует

**BookingService** публикует событие `BookingConfirmed` после подтверждения брони.

### Кто подписан

**EventService** подписан на событие `BookingConfirmed`.

### Что происходит при получении

1. **BookingService** подтверждает бронь (статус → Confirmed)
2. **BookingService** публикует `BookingConfirmed` с `BookingId`, `EventId`, `UserId`
3. **EventService** получает событие
4. **EventService** уменьшает `AvailableSeats` на 1
5. Если места закончились — событие становится недоступным для бронирования

### Запуск

Для поднятия баз данных и kafka используется docker-compose.yml
В терминале, в корне решения необходимо выполнить следующую команду:

```bash

```

## Формат ответа при ошибках

При возникновении ошибок API возвращает JSON-ответ в следующем формате:

```json
{
  "status": <код_статуса>,
  "detail": "<сообщение_об_ошибке>"
}
```

### HTTP статусы:

| Статус | Описание                                               |
|--------|--------------------------------------------------------|
| 400    | 	Ошибка валидации (некорректные данные запроса)        
| 404    | 	Ресурс не найден (событие с указанным ID отсутствует) 
| 409    | При отсутствии мест возвращается 409 Conflict          
| 500    | 	Внутренняя ошибка сервера                             

### Модель Event

| Поле                                | Описание                         |

### Пример сценария использования

1. Создаём событие
2. По id события создаём бронирование
3. Бронирование создаётся со статусом "Pending"
4. В фоне происходит обработка бронирования и переход статуса в "Confirmed"

## 🏗️ Clean Architecture

Проект построен по принципам чистой архитектуры. Разделение на отдельные сборки гарантирует соблюдение направления
зависимостей:
внешние слои зависят от внутренних, но не наоборот.

### Назначение слоёв

#### 🟣 Domain (Class Library)

Самый внутренний слой. Содержит бизнес-правила и не зависит ни от чего внешнего.

- **Entities** — доменные сущности (`Event`, `Booking`)
- **Value Objects** — объекты-значения
- **Domain Exceptions** — доменные исключения (`NotFoundException`, `ValidationException`)

#### 🟢 Application (Class Library)

Слой use cases и бизнес-логики приложения. Зависит **только от Domain**.

- **Services** — сервисы приложения (`EventService`, `BookingService`)
- **Interfaces** — интерфейсы портов (`IEventRepository`, `IBookingRepository`)
- **DTOs** — объекты передачи данных (`CreateEvent`, `BookingInfo`)
- **Background Services** — фоновые задачи (`BookingBackgroundService`)

#### 🔴 Infrastructure (Class Library)

Реализует доступ к данным и взаимодействие с внешними системами. Зависит от **Domain и Application**.

- **DataAccess** — `AppDbContext`, миграции EF Core
- **Repositories** — реализации репозиториев (`EventRepository`, `BookingRepository`)
- **Configurations** — конфигурации сущностей (`IEntityTypeConfiguration`)

#### 🔵 Presentation (Web API)

Точка входа в приложение. Зависит от **всех слоёв**.

- **Endpoints** — Minimal API эндпоинты
- **Exception Handling** — обработчики исключений (`GlobalExceptionHandler`)
- **DI Registration** — регистрация зависимостей

## 🔐 Ролевая модель и разграничение прав

В системе реализованы две роли пользователей:

| Роль      | Описание             | Права                                                                             |
|-----------|----------------------|-----------------------------------------------------------------------------------|
| **User**  | Обычный пользователь | Создание бронирований, просмотр и отмена своих броней                             |
| **Admin** | Администратор        | Все права User + создание, редактирование и удаление событий, отмена любых броней |

|--------------------------|------------|-----------------|-----------|

| `POST /auth/login`       | ✅          | ✅               | ✅         |
| `GET /events`            | ✅          | ✅               | ✅         |
| `POST /events/{id}/book` | ❌ 401      | ✅               | ✅         |

## 🔑 Получение JWT-токена через Swagger

### 1. Запустите приложение

### 2. Откройте Swagger UI

### 3. Зарегистрируйте пользователя

Выполните POST /auth/register со следующим телом запроса:

```json 
{
  "login": "admin",
  "password": "admin123"
}
```

- role: 0 — обычный пользователь (User)
- role: 1 — администратор (Admin)

### 4. Получите токен

Выполните POST /auth/login:

```json
{
  "login": "admin",
  "password": "admin123"
}
```

### 5. Вставьте токен в Swagger

- Нажмите кнопку Authorize (замочек в правом верхнем углу)
- Вставьте полученный токен (без кавычек)
- Нажмите Authorize
- Закройте модальное окно

Теперь все защищённые эндпоинты будут работать. Для смены пользователя нажмите Logout и вставьте новый токен.

## ⚙️ Настройка секрета JWT

Параметры JWT задаются в файле appsettings.json:

```json
{
  "Jwt": {
    "SecretKey": "your-super-secret-key-at-least-32-characters-long!",
    "Issuer": "EventApi",
    "Audience": "EventApi",
    "ExpirationMinutes": 60
  }
}
```

| Параметр          | 	Описание                                                  
|-------------------|------------------------------------------------------------|
| SecretKey         | 	Секретный ключ для подписи токена (не короче 32 символов) 
| Issuer            | 	Издатель токена                                           
| Audience          | 	Аудитория токена                                          
| ExpirationMinutes | 	Время жизни токена в минутах                              

# Кеширование

## Что кешируется

- **Событие по идентификатору** (`GET /events/{id}`) — TTL `EventTtl` (10 минут).
- **Топ-10 популярных событий** — TTL `TopEventsTtl` (5 минут).

Стандартный TTL для прочих записей — `DefaultTtl` (5 минут).

## Почему кешируем

- **Событие по id** — самая частая операция чтения, данные меняются редко.
- **Топ-10** — тяжёлая агрегация по БД, результат меняется нечасто.

## Выбор TTL по типам

| Ключ           | TTL    | Обоснование                                           |
|----------------|--------|-------------------------------------------------------|
| `DefaultTtl`   | 5 мин  | Базовое значение для неспецифичных записей            |
| `EventTtl`     | 10 мин | Данные события стабильны, редкие обновления           |
| `TopEventsTtl` | 5 мин  | Баланс между актуальностью рейтинга и нагрузкой на БД |

## Инвалидация

- **При записи** — обновление/создание события инвалидирует соответствующий ключ события.
- **По Kafka-событиям** — при получении события из Kafka происходит явная инвалидация кеша события и топа.
- **По TTL** — все ключи автоматически истекают по своему TTL.

## Поведение при недоступности Redis

Если Redis недоступен:

- Приложение стартует - подключение инициализируется **лениво** через фабрику `sp => ConnectionMultiplexer.Connect(...)`,
  поэтому попытка коннекта не блокирует запуск.
- Запросы идут в БД — кеш не используется.
- При восстановлении Redis кеш прогревается автоматически при последующих запросах.
